## 2. 先理解几个 NixOS 概念

| 概念 | 通俗解释 | 对本项目的意义 |
| --- | --- | --- |
| 声明式配置 | 在配置文件中写“我要哪些软件、服务和设置”，由系统生成相应环境 | 设备适配、挂载、网络和服务都应写成 NixOS 模块 |
| Nix store | 软件及依赖存放在 `/nix/store`，不同版本可以并存 | 不照搬 Ubuntu 的 `/usr`、Deb 包或 ArmadaOS 的系统目录 |
| 系统代际（generation） | 每次部署保存一套系统软件及配置的构建结果 | 启动菜单应能选择当前代际及保留的旧代际 |
| 回退 | 重新使用保留的系统代际 | 能回退系统软件和声明的配置，但不会自动恢复个人文件、数据库或所有 `/var` 状态 |
| Flake 与锁文件 | 为项目提供统一构建入口，并记录依赖的精确版本 | 推荐使用；用户日常主要编辑易读的配置模块，无需一开始掌握全部语法 |
| 二进制缓存 | 下载别人已经构建好的、经过校验的软件包 | 平板更新通常不必从源码编译整个系统；设备内核等定制内容可能例外 |

NixOS 也能手动装软件、修改文件，但本项目交付的硬件支持必须能从配置重建。不能依赖“先执行一串没记录的命令，系统才正常”。

`system.stateVersion` 是数据兼容默认值的基准，不是升级开关。首次安装时选定，后续升级软件不应顺手修改它。

## 3. 启动架构

```text
设备 Bootloader
  └─ Android boot 镜像中的 kShimC 菜单
      ├─ Android：继续原厂启动路径
      └─ Linux：只读访问独立 ext4 /boot
          └─ NixOS → 选择系统代际
              ├─ ARM64 Image
              ├─ 与该内核配套的完整设备树 DTB
              └─ NixOS 生成的 initramfs
                  └─ 挂载 Btrfs 子卷及 Nix store
                      └─ 启动选定代际的 /nix/store/.../init
                          └─ systemd → 命令行与网络服务
```

这里的 Linux `/boot` 是新增的 ext4 文件系统，**不是 Android 的 `boot_a` / `boot_b` 分区**。首次安装菜单涉及 Android boot 镜像；正常 NixOS 更新只发布外置启动文件，不应每次重刷 Android 启动分区。

本路线不以 UEFI 为前提，首版不引入 GRUB、systemd-boot 或 FAT ESP。使用 NixOS 的外部启动器接口接入 kShimC。initramfs 使用 NixOS 的构建机制，移植必要的设备初始化逻辑，不直接沿用 Ubuntu 的手写根系统启动脚本或 ArmadaOS 的 dracut/OSTree 启动过程。

需要验证：原厂固件与 kShimC 的组合、Android 返回路径、设备树交接、内核进入 NixOS initramfs、挂载 Btrfs、执行指定代际的 init。

## 4. 存储布局

### 4.1 物理分区

| 区域 | 文件系统与容量 | 用途 |
| --- | --- | --- |
| Android 原有启动、固件及其他必要分区 | 以实机 GPT 和原厂要求为准 | 保留 Android 启动及设备必需数据 |
| Android userdata | 容量待核算 | 为 Linux 腾出空间后保留 Android 的用户数据区域 |
| Linux boot | ext4，1 GiB，已确定 | 存放 kShimC 配置及各代际启动载荷 |
| Linux root | Btrfs，约 200 G，已确定 | 系统、Nix store、用户目录及持久状态 |

约 200 G 的实际可行性取决于设备总容量、Android 剩余空间需求及分区边界。先只读采集 GPT、逻辑扇区大小和文件系统信息，再给出起止位置与最终容量；不按参考项目中的 `/dev/sda16`、`/dev/sda17` 直接操作。

**首次划分 Linux 空间可能需要备份、重建 Android userdata 并恢复数据。** 不预设 Android 文件系统支持无损缩小，也不把桌面 Linux 的分区工具用法直接套在 Android 动态分区上。是否接受 Android 数据清空，是实施前必须讨论的事项。

识别分区使用 PARTUUID / GPT PARTLABEL，挂载文件系统使用匹配的 UUID / 子卷配置，避免依赖易变化的 `/dev/sdX` 编号。具体 GPT 标签要与 kShimC 配置一致；不会为了名称整齐而要求改动已验证的加载器配置。

### 4.2 Btrfs 子卷建议

建议一个 Btrfs 分区，先使用少量子卷，不为 `/home`、`/nix` 再切固定容量的物理分区。

| 子卷名称（建议） | 挂载点 | 理由 |
| --- | --- | --- |
| `@nixos-root` | `/` | 保存系统可变状态与系统配置 |
| `@nixos-nix` | `/nix` | 将 Nix store 和 Nix 数据库从根子卷快照中分离 |
| `@nixos-home` | `/home` | 个人数据独立于根子卷 |
| `@nixos-log` | `/var/log` | 日志单独管理，设置容量限制 |

这些子卷共享约 200 G 空间，并不各占一份预留容量。首版不启用配额、自动根快照恢复、临时根文件系统或每次启动清空根目录等额外机制。

建议启用轻量的 `compress=zstd:1`，定期检查空间。TRIM 策略在验证 UFS 与内核支持后确定。`/nix` 需要在启动早期可用，不能等系统服务启动后再挂载。

建议首版使用 zram 处理内存压力，不创建磁盘 swap，也不承诺休眠到磁盘。若后续确需 Btrfs swapfile，单独验证无压缩、映射及内核约束；suspend 挂起与磁盘休眠是两个独立问题。

### 4.3 ext4 /boot 的特殊要求

- kShimC 要求干净且特性受支持的 ext4；它不回放 journal，也不修复文件系统。创建参数必须通过其读取器检查。
- 建议日常将 `/boot` 挂载为只读，仅发布更新时临时写入。发布结束同步文件、目录和文件系统，并恢复只读，验证加载器能接受其状态。
- 更新时若意外断电，即使文件原子发布正确，ext4 仍可能需要日志回放。恢复路径是 Android/独立维护环境下修复，不能只指望菜单选择旧代际。
- 1 GiB 是固定预算。发布前计算启动载荷、保留版本和临时写入所需空间；空间不足应中止，不以删除最后一个已验证版本来强行更新。

两个参考项目提供不同价值，应分别核对来源和适用条件。

| 来源 | 当前查阅到的内容 | 规划中的用途与限制 |

| 独立 `kShimC-oneplus-pad2-pro` | ext4 外置启动文件协议、多系统/多版本选择及原子发布工具 | 作为本项目唯一菜单接口来源，不从两个发行版各复制一套菜单实现 |

建议先评估 mainline 项目锁定的内核和设备树，用小型诊断 initramfs 验证 kShimC 交接；若遇到启动阻碍，利用 ArmadaOS 已验证链路定位差异。确定一套通过验证的组合后，首版只维护这一套内核，不同时长期维护两条发行分支。

内核和必要的外部模块最终都用 Nix derivation 描述构建，固定源码提交、补丁、配置和哈希。允许临时利用已有产物做诊断，但它们不能成为正式系统的隐含依赖。

## 6. 系统代际与 kShimC 的集成

这是本项目除硬件之外的核心开发项。

建议通过 `boot.loader.external.installHook` 实现 NixOS 启动文件安装器，读取目标代际的 Bootspec / 系统构建输出，为每个可启动代际生成完整的 kShimC 条目。具体接口以最终锁定的 Nixpkgs 版本为准。

```text
/boot/kshim/
├── boot.conf                         # 共享系统列表
└── systems/nixos/
    ├── entries.conf                  # 当前、前一版本与菜单条目
    └── versions/<唯一代际ID>/
        ├── manifest.conf            # 大小、摘要和完整命令行
        ├── Image
        ├── board.dtb
        └── initramfs.img
```

安装器需要满足以下行为：

1. 每个代际对应自己的内核、模块、DTB、initramfs、内核参数及准确的 NixOS init store 路径。仅复制内核并切换 `current` 不足以实现系统回退。
2. `/boot` 存放实际文件，不依赖软链接到 `/nix/store`；kShimC 禁止此类软链接路径。
3. 使用新 ID 和临时目录准备载荷，校验大小与 SHA-256，完成同步后再原子更新版本选择器。使用协议要求的系统锁和全局锁。
4. 为保留在启动菜单中的代际保留 Nix GC roots，防止垃圾回收删掉其 init、模块和依赖。只保留 `/boot` 的文件并不能保护根系统闭包。
5. 版本清理先移除菜单引用，再解除相关 GC 保留；不得删除当前运行、当前默认或明确标记为救援的代际。
6. 合并共享 `boot.conf` 时保留其他 Linux 系统配置，不接管整个分区。
7. 明确实现并验证 `nixos-rebuild boot`、`switch`、`test` 和回退的区别。`test` 不应改变持久启动默认；`switch` 不代表运行中的内核立刻切换。
8. 发布失败返回错误并保留可用旧入口。Nix profile、启动菜单和运行服务不是跨文件系统的单一事务，需记录状态并能重试、核对和修复，不能承诺完全原子升级。

建议菜单常规保留 4 个启动代际，其中至少一个标记为已验证的救援版本；具体数量受 1 GiB 实际空间限制。新版 kShimC 对启动版本分页显示，版本列表仍受配置文件大小限制。

初期关闭激进的自动代际删除和自动 GC，先完成“更新—启动—回退—清理—再启动”的验证闭环，再启用有保留策略的清理。

**当前 kShimC 没有启动失败计数和自动回退。** 第一版提供菜单手动选择旧代际。自动失败回退如要实现，需要加载器与系统成功标记协作，应作为后续独立功能。

## 7. 基本系统的建议配置

| 项目 | 建议 | 理由 / 后续选择 |
| --- | --- | --- |
| Nixpkgs 渠道 | 实施时仍受支持的稳定分支，并锁定具体提交 | 先降低系统层变化；确需新驱动时对相应包单独覆盖，避免混用整套不同渠道 |
| 配置入口 | Flake + `flake.lock` + 可复用 NixOS 模块 | 明确输入版本，设备支持与用户偏好分开 |
| initramfs | 优先评估 systemd initrd | 用声明式服务表达早期挂载、模块和诊断；以选定版本及设备验证结果决定 |
| 本地界面 | 文本控制台、清晰字体、可见启动日志 | 不安装显示管理器或桌面 |
| 网络 | NetworkManager，提供 `nmcli` | 方便命令行配置 Wi-Fi，也方便用户后续安装桌面 |
| 管理访问 | OpenSSH，密钥认证、普通用户提权 | USB 网络也使用认证 SSH，不直接移植参考项目的免认证 root shell |
| 首次接入 | 优先 USB 网络 + SSH；本地键盘作为补充 | Wi-Fi 凭据不写进公共配置；NCM 重插问题需验证恢复方法 |
| 账户 | 一个普通管理用户 | 用户名、公钥与本地密码设置方式待确定 |
| 基础工具 | Nix、Git、编辑器、网络诊断、Btrfs/ext4 工具 | 满足维护与故障排查，避免塞入大型应用集合 |
| 内存与交换 | zram，参数根据实际内存确定 | 降低存储写入，先不引入磁盘休眠链路 |
| 日志 | 持久 journal，设置空间上限 | 能分析上次启动，也避免挤占系统空间 |
| 自动升级 | 初期手动更新，不自动重启 | 每次内核/启动链更新都应可观察、可回退 |
| 桌面、Home Manager | 首版不安装、不设为依赖 | 用户后续按需求增加 |

无桌面不等于没有硬件支持：充电、温控、电量读取、关机、网络和存储仍是基本系统的重要组成部分。GPU/Mesa、音频、传感器等做成可选模块，但不为了“无桌面”删掉保证设备正常运行的底层驱动。

扬声器、实验性电源管理等功能只有在所选组合下验证后才启用。参考项目提到的扬声器保护与温控限制需要继续跟踪。基础系统可用不代表所有硬件或后续任意桌面都已验证。

## 8. 构建与日后维护

目标架构是 `aarch64-linux`，当前电脑是 `x86_64`，且本次检查未发现可直接使用的 `nix` 命令。构建环境准备列为实施任务，本阶段不安装工具或修改主机配置。

建议先使用官方 ARM64 二进制缓存，并评估电脑上的 QEMU/binfmt ARM64 构建环境；有真实 ARM64 builder 时可以替换。内核另评估 Nix 管理的交叉编译，以减少模拟构建耗时。整个 NixOS 直接全量交叉构建不是首选，因为包支持和缓存命中与原生 ARM64 构建不同。

构建不能依赖本机另一个工作目录的未提交输出。正式输入固定为可获取的源码、明确授权的本地固件输入及哈希。锁文件能固定输入，但并不自动保证所有底层构建字节完全相同，仍需产物与闭包检查。

平板能启动后，支持本机从同一份配置执行构建和部署；下载命中缓存的包，必要时编译定制内容。电脑继续可选地提供远程构建或包缓存。自建缓存只信任用户明确配置的签名密钥，不要求开放免认证服务。

建议项目结构如下，实际实施时再创建配置文件：

```text
flake.nix / flake.lock
modules/oneplus-pad2pro/       # 内核、设备树、固件与设备服务
modules/kshim/                # 外部启动器、代际发布与清理
hosts/pad2pro/                # 本机文件系统与用户配置
packages/                     # 内核与必须移植的辅助程序
tools/                        # 输入核对、产物检查与部署工具
docs/                         # 安装、更新、回退和恢复说明
```

预期日常流程是：修改配置 → 构建 → 检查变更与空间 → 发布新代际 → 重启选择 → 验证 → 保留或回退。优先用 `nixos-rebuild boot` 安排涉及内核和关键硬件的更新；日常服务调整在集成验证后可用 `switch`。

## 9. 分阶段实施与验收

| 阶段 | 工作 | 通过标准 |
| --- | --- | --- |
| P0：敲定方案 | 完成设备信息、分区容量、备份方式、账户和接入方式的讨论 | 本文的关键待定项有明确结论 |
| P1：输入和环境 | 固定 Nixpkgs、内核、DTB、固件和菜单版本，准备 Nix 构建环境 | 基础配置可求值；设备源码、固件和架构可核验 |
| P2：诊断启动 | 生成小型诊断 initramfs，通过临时启动检查 kShimC → 内核 → initramfs | 明确的构建身份、日志和设备信息；Android 路径可返回；不自动格式化磁盘 |
| P3：基本系统离线构建 | 构建 NixOS 闭包、initramfs、启动载荷及安装材料 | 能检查内容、模块依赖和根挂载参数；载荷通过加载器检查 |
| P4：首次安装 | 在备份和具体布局确认后新增分区、部署 Btrfs 系统与外置启动文件 | 从存储启动进入文本系统，能通过 SSH 管理 |
| P5：硬件与启动验收 | 检查读写、网络、充电、电量、温度、关机、重启及 Android 共存 | 每项分别记录结果、版本和限制；断电后的重启仍能正常进入系统 |
| P6：更新与回退 | 两个不同系统代际、手选回退、清理与失败发布验证 | 老代际能加载其配套系统；GC 后保留代际仍可启动；失败不破坏已有入口 |
| P7：整理交付 | 输出可重建配置、安装说明、已知问题和恢复步骤 | 用户能照文档更新、回退，并在需要时恢复 Android 启动 |

P2 的诊断镜像与 P4 的正式安装分开，避免排查内核时同时引入分区和根系统问题。临时启动只证明启动链中的对应部分，不能替代正式根系统、更新和恢复验收。

实机操作按具体任务另行安排，默认先提供带版本与摘要的临时测试产物和命令，由用户执行、反馈；只有用户明确要求代操作时才执行。规划阶段不会据此自动重启或刷写设备。

## 10. 恢复与长期维护边界

- 记录匹配当前 Android 固件的原厂启动镜像、GPT 布局与恢复入口；设备校准数据单独备份，不跨设备复用。
- 保留一套可从电脑临时启动的维护环境，用于根文件系统故障、ext4 journal 恢复和菜单修复。它不依赖损坏系统里的 `/nix/store` 才能启动。
- NixOS 代际回退不替代 Btrfs 数据快照和异机备份。将来启用快照时分别定义 `/home`、`/var` 和 `/nix` 的一致性与保留策略，首版不自动恢复快照。
- Android OTA 可能覆盖菜单所在启动镜像或改变固件组合；升级前记录状态，升级后重新验证菜单与两个系统。首版不承诺所有 OTA 都可直接兼容。
- 启动文件的 SHA-256 检查用于发现损坏或不一致，不等同于签名认证或恢复 Android Verified Boot 的信任链。
