# linux-sm8750-erhai-patchset 实施计划

## 目标

将 OnePlus Pad 2 Pro（OPD2413 / Erhai / SM8750）支持整理为可独立发布、按顺序重放的内核补丁集。NixOS 使用 nixpkgs 提供的上游正式发布源码，构建时应用补丁；同一受维护系列随 nixpkgs 更新，跨系列升级单独适配。产物仍是设备定制内核。

项目名及目录采用 `linux-sm8750-erhai-patchset`。

## 边界与约束

- 现有开发树：`/zpool/storage_01/build/LinuxForOneplus/linux-sm8750-erhai`。保留其开发、调试和上游同步用途，不重写已发布历史。
- NixOS 项目：`/zpool/storage_01/build/LinuxForOneplus/NixOS_for_OnePlus-Pad2Pro`。
- 本项目负责补丁、通用硬件配置、来源记录及验证工具；NixOS 配置、打包、固件安装、服务、initrd 和 kShimC 发布属于 NixOS 项目。
- 补丁分支是修改的维护来源，补丁文件由提交导出；不得让完整源码与补丁独立手工维护。设备支持必须可脱离 NixOS、使用标准 Kbuild 构建。
- 所有 Nix 构建及模块聚合使用同一当前 nixpkgs 工具链。依赖锁定用于复现，不以历史工具链、闭包路径或二进制哈希阻止更新。
- 内核适配只向前推进，不降级、不向更旧系列移植、不增加旧内核兼容分支；更新失败时修复目标版本的补丁，不改用较旧内核。
- 保留现有可启动代际作为故障恢复手段，不为其新增适配或长期维护；候选实机验证后再切换日常默认。不得静默跳过失败补丁或关闭关键配置检查。

## 实施顺序

### 1. 建立可核验基线

- 读取相关仓库的 `AGENTS.md`，记录工作区状态，保留已有修改。
- 重新确认当前设备提交、正式上游基线、nixpkgs 锁定版本、内核配置及启动方式。2026-11-13 的参考是设备提交 `efc39b9d972665c270adc4e4ec2c46685792ffda`、Linux `7.2.15` 提交 `497791a0a96b866d90add64041c47acdff49cae6`。
- 内核仓库是浅克隆，按需补齐相关历史，不能把可见提交数量当成完整补丁数量。参考差异为 279 个文件；它包含非必需功能，尚未完成依赖筛选。
- 核验上游来源，导出完整差异作为迁移检查点；从干净上游源码重放，比较源码树，确认没有漏掉驱动、DTS、Kconfig、绑定或测试。该检查点不作为长期单体补丁发布。

### 2. 整理并发布补丁集

- 从明确上游基线创建专用补丁分支，按“平台依赖 → 设备驱动与 DTS → 可选功能”拆分提交；避免混入上游已有的 stable 提交和重复补丁。
- 先保持现有功能，再逐项确认可选内容及依赖；不能仅凭目录或驱动名称删除代码。
- 每项修改保留作者、许可证、来源、依赖和上游状态。导出补丁时固定顺序；记录目标版本、源码哈希、补丁提交和配置来源。
- 建议最小布局：

```text
README.md                         # 标准 Kbuild 使用方式、维护流程
patchsets/<major.minor>/
  manifest.json                   # 上游基线、来源、依赖、补丁集版本
  series                          # 明确应用顺序
  patches/*.patch
configs/*.config                  # 通用硬件配置，不含 NixOS 配置
tools/                            # 导出、重放、检查工具
tests/                            # 迁移已有相关回归检查
```

### 3. 移植到受维护的正式系列

- 重新检查 nixpkgs 可用内核和上游维护状态，以实施时 `linuxPackages_latest` 对应的受维护正式系列为初始目标，且不得低于设备当前版本。编写时该目标为 7.3；7.2.15 仅用于源码差异提取与还原检查，不作为新适配或发布目标。
- 向目标系列逐项重放、修复 API 变化、删除已进入上游的补丁。遇到语义变化时核对行为，不能只修到编译通过。
- 日常跟随已适配系列的补丁版本；下一正式系列作为候选持续适配，在当前系列停止维护前完成切换。初始迁移不同时大幅裁剪配置。
- 把补丁栈作为正式维护对象，避免长期维护一个巨大 diff 
- 当前支持覆盖显示、触控、音频、充电、休眠、Wi‑Fi、蓝牙等多个子系统，移植时要避免遗漏。建议按依赖和用途组织

### 4. 接入 NixOS

- 显式选择目标正式系列的 nixpkgs 内核包，避免隐式使用默认 `pkgs.linuxPackages` 导致降级；复用 `boot.kernelPatches` 和 `structuredExtraConfig`，保留必要补丁及 NixOS 通用配置。移除自定义打包中写死的内核版本和 fork 源码依赖。
- 必须先应用设备补丁，再生成 `.config`；配置生成和内核编译使用同一份有效源码。迁移 NixOS 项目的 `packages/nixos.config` 时保留其语义，检查最终配置而非只检查输入片段。
- DTB、内核模块、initrd 及启动发布统一引用最终 `config.boot.kernelPackages.kernel`；修正当前从基础 `cfg.kernelPackage` 取 DTB 的路径。
- CPS8601 修复进入补丁集并验证后，取消重复覆盖模块路径。保留匹配的 OEM 固件、板级配置与用户空间服务。
- 版本及模块目录信息由选定上游版本和补丁集标识生成；保留 x86_64 → ARM64 构建能力，以及 kShimC 的 `Image`、DTB、initrd 和代际关联。
- 更新 NixOS 文档、flake 输入和现有相关检查，清理不再使用的 Nix 包变体和源码输入；保留回退闭包和历史验证记录。

### 5. 验证并切换

- 自动检查：干净上游源码可按 `series` 无模糊匹配地重放；关键 Kconfig 生效；已有相关驱动回归检查通过；完整内核、模块、DTB、initrd 和启动发布检查通过。
- 实机检查：候选身份正确；冷启动和普通重启；存储；显示、触控和 GPU；音频；Wi-Fi 自动发现与联网；蓝牙；充电、电量；休眠恢复。记录通过、失败和未测范围。
- 经候选启动完成约定的设备验收后切换默认，确认 kShimC 回退仍可用。源码等价、编译成功和实机通过分别记录，不能互相替代。
- 验证一次新上游补丁版本的维护流程；若暂无新版本，明确记录该项待验证，不虚报已支持自动升级。

## 完成标准

独立项目可从明确的官方源码重建设备支持，不依赖旧 fork 工作区；NixOS 消费固定版本补丁集并使用当前 nixpkgs 工具链；关键功能完成实机验收且保留启动回退；README 足以让后续 Agent 完成“更新基线 → 重放/修补 → 构建 → 实机验证 → 发布”的维护循环。
